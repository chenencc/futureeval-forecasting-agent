# Saved-source selection acquisition comparison

The manual `source_selection_binary_ten.yaml` workflow evaluates Mercury as a discovery-lead selector. It does not replace the production collection agent, invoke forecast analysis, or submit forecasts. Production remains pinned to `v1.0.1`.

Ten fixed binary development questions use source run 36948699455. The selector sees only the original question/rules, search titles/snippets/dates, question links, and metadata-only URLs previously captured. It never receives old page bodies, analysis outputs, resolution labels or prior selection annotations. Version 2 asks one opening-priority head per candidate with shared entity, event-window, source-detail and event-stage instructions. Titles and snippets are bounded to 100 and 160 characters. Compact batches still obey the 28,000-byte request ceiling. These decisions are relevance hypotheses, not validated facts.

Each task has fresh isolated A/B ledgers explicitly authorized by the user. A recaptures the old actual page-selection order; B captures Mercury's selected candidates. Both reuse the original `RetrievalTask.read_sources` implementation and the independent supplemental repair toolchain. The old agent-generated need plan is reused without restarting its reasoning loop. Top-K is equal between arms: min(8, prior unique page attempts). Mercury may skip confidently unrelated sources. Shared body caching is disabled and arm order alternates. Current-page changes remain a limitation despite contemporaneous recapture.

All saved searches are replayed as discovery leads; no new Tavily or Exa searches are necessary for this selection experiment. The original three-basic-search ceiling remains available in the collection framework but is not exercised. Basic Extract is disabled equally between arms; independent saved-byte, HTTP and bounded Playwright repair remains enabled. This isolates candidate selection rather than measuring a newly generated search strategy. Historical captures are retained as an additional descriptive reference, not treated as contemporaneous controls.

One physical Mercury attempt is reserved per dynamically byte-bounded candidate batch. Each request is at most 28,000 bytes. Interrupted reservations, failed calls, captured originals, repair child hashes and frozen identities persist across `resume_run`. A restored experiment never resets its fresh arm budgets again. Evaluation distinguishes model-claimed exact relevance from independently inspected readable text, correct time scope, exact actor/metric and original authority/detail coverage. Readability and domain counts alone are not evidence of resolving-condition coverage.

## Version 2 acquisition guards

Exact URLs cited in resolution criteria receive reserved slots before model ranking. Glossary/definition links and background links are not automatically reserved. Reservations never increase top-K; excess rule sources are recorded in `rule_source_overflow_ids`. Explicitly conflicting issuer identifiers override reservations.

An optional `target_issuer` contract contains `name`, `cik`, and subsidiary `aliases`. For filing questions, a simple target name can be inferred from the question. A supplied CIK can be compared with an EDGAR path; without one, a regulator domain or opaque accession number remains unknown. Explicit filer names can be checked in metadata and after capture. Matching names does not establish filing type, public status or event timing. When a rule permits subsidiaries and the target was inferred, a different filer is quarantined as `unverified_affiliate`, not asserted to be unrelated. Declared aliases can establish the identity mapping.

Both experimental arms screen captured bodies with the same observable quality and issuer checks. Navigation/login shells and explicit filer-name conflicts move to `selection_excluded_pages`; their exact original content and repair attempts remain archived. `selection_acquisition_gaps` and `selection-diagnostics.json` explain exclusions. Numeric tables and short substantive notices remain eligible. No replacement fetching, automatic retries or extra searches are triggered by these checks.

Version 2 requires a fresh output directory. It must not resume version 1 identities or mutate their ledgers. Offline saved-corpus checks estimate request counts and exercise guards without calling providers; they do not establish the quality of new Mercury rankings.

Run an offline review using `python -m ForecastAgent.source_selection_replay --inputs PATH_TO_COMPLETED_TRIAL --output PATH_TO_REPORT.json`. The input root contains the two batch artifact directories. On the completed ten-case corpus from run 37037826340, the compact format requires 11 bounded requests for 293 priority heads, versus 44 actual version 1 requests and 1,172 heads. This is a request-count estimate, not a measured token or ranking-quality improvement. Neither offline review nor body screening consumes provider or search budgets.
